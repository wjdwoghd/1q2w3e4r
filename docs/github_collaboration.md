# GitHub 협업 원칙

이 문서는 작업 등록, 브랜치, 커밋, 코드 리뷰와 산출물 공유 기준을 정한다. 프로젝트의 구조와 분석 원칙은 [AGENTS.md](../AGENTS.md), 구현 규칙은 [코드 작성 원칙](./coding_conventions.md), 개발 순서는 [ROADMAP.md](../ROADMAP.md)를 함께 따른다.

## 참고 자료와 적용 범위

- 제공된 `Project Convention`의 경량 Git Flow, 한글 커밋, Issue 및 PR 중심 협업 방식을 반영한다.
- 제공된 `코르티스 취약 사내망 웹 서비스 구축 및 모의해킹 | Team REDRED`의 담당자별 진행 기록, 증적 관리, 통합 환경 검증 방식을 반영한다.
- 참고 프로젝트의 개발 기간, 머신러닝 구성, 공격 절차, 구현 완료 주장은 이 프로젝트에 적용하지 않는다.
- 코드와 버전 이력은 GitHub를 기준으로 관리한다. Notion에는 기획, 회의, 진행 현황과 접근이 제한된 증적을 정리하고 관련 Issue, PR, 커밋을 연결한다.

## 작업 등록과 소통

1. 작업 전에 Issue에 목적, 범위, 담당자, 관련 경로와 완료 조건을 적는다.
2. 진행 상태를 시작 전, 진행 중, 검토 중, 완료로 관리한다. 막힌 작업은 원인과 필요한 결정을 기록한다.
3. 공통 인터페이스, Risk Rule, DB Schema 변경은 관련 담당자와 영향 범위를 먼저 공유한다.
4. 코드와 설계가 달라지면 같은 PR에서 관련 문서를 갱신한다.
5. 개선 제안과 질문은 Issue 또는 PR에 남겨 결정 근거를 추적할 수 있게 한다.

## 브랜치 전략

경량 Git Flow를 사용하며 별도 `release` 브랜치는 운영하지 않는다. 아래는 운영 규칙이며 문서 작성만으로 브랜치나 보호 설정이 생성되지는 않는다.

| 브랜치 | 분기 기준 | 용도 | 병합 대상 |
| --- | --- | --- | --- |
| `main` | 통합 완료 상태 | 최종 배포 및 발표 버전 | 해당 없음 |
| `develop` | 초기에는 `main` | 기능 통합과 검증 | `main` |
| `feat/<작업명>` | `develop` | 기능 개발 | `develop` |
| `fix/<작업명>` | `develop` | 일반 오류 수정 | `develop` |
| `docs/<작업명>` | `develop` | 문서 작성 및 수정 | `develop` |
| `hotfix/<작업명>` | `main` | 배포 후 긴급 수정 | `main`, `develop` |

브랜치는 한 가지 작업 목적에 맞추고 작업명은 짧은 영문 소문자와 하이픈을 사용한다. 예: `feat/sbom-parser`, `fix/risk-threshold`, `docs/collaboration-rules`.

### 기능 개발 순서

다음 명령은 원격 `develop`이 준비되어 있고 현재 작업 디렉터리에 미반영 변경이 없는 경우의 예시이다. 아직 `develop`이 없다면 저장소 관리자가 기준 커밋을 정해 먼저 생성하고 공유한다.

```bash
git status
git switch develop
git pull --ff-only origin develop
git switch -c feat/sbom-parser
```

개발과 관련 검증 후 변경한 파일을 명시하여 스테이징한다.

```bash
git diff --check
git add core/sbom/parser.py tests/unit/test_sbom.py
git diff --cached
git commit -m 'feat: CycloneDX SBOM 파서 구현'
git push -u origin feat/sbom-parser
```

GitHub에서 대상 브랜치를 `develop`으로 지정하여 PR을 생성한다. 통합 검증을 마치면 `develop`에서 `main`으로 PR을 생성한다. 긴급 수정은 `main`에서 분기하고 수정 결과를 두 브랜치에 모두 반영한다.

## 커밋 메시지

제목은 `<type>: <한글 설명>`으로 작성하며 한 커밋에는 한 가지 작업 목적만 포함한다. 병합 및 squash 커밋 제목에도 같은 규칙을 적용한다. 본문이 필요하면 변경 이유, 영향 범위와 관련 Issue를 기록한다.

| Type | 용도 |
| --- | --- |
| `feat` | 새로운 기능 |
| `fix` | 일반 오류 수정 |
| `hotfix` | 긴급 오류 수정 |
| `refactor` | 동작을 유지하는 구조 개선 |
| `style` | 코드 형식 및 UI 스타일 |
| `docs` | 문서 작성 및 수정 |
| `test` | 테스트 작성 및 수정 |
| `comment` | 주석 작성 및 수정 |
| `rename` | 파일 또는 디렉터리 이름 변경 |
| `remove` | 불필요한 파일 또는 코드 삭제 |
| `chore` | 빌드 및 환경 설정 |

```text
feat: 자산 맥락 기반 대응 우선순위 계산 추가
fix: 우선순위 등급 경계값 처리 오류 수정
docs: GitHub 협업 및 코드 작성 원칙 정리
test: 개선 검증 증적 누락 사례 추가
```

현재 `commit-msg` Hook은 구현되어 있지 않다. 리뷰에서 메시지를 확인하며, Hook이 준비되기 전에는 `.githooks` 활성화 명령을 실행하지 않는다.

## PR과 리뷰

PR에는 다음 내용을 기록한다.

- 관련 Issue, 변경 목적과 변경 전후 동작
- 주요 변경 파일과 공통 모듈, 설정, 데이터 구조에 미치는 영향
- 수행한 검증 명령과 실제 결과, 실행하지 못한 검증과 사유
- 결과를 확인할 수 있는 민감정보 제거 증적
- 남은 문제, 후속 작업 및 필요한 경우 되돌리는 방법

다른 팀원 1명 이상의 리뷰를 원칙으로 하며, 리뷰 의견에 대한 수정 또는 합의와 관련 검증을 완료한 뒤 병합한다. 자기 승인만으로 검토 완료를 표시하지 않는다. `main`과 `develop`의 PR 및 리뷰 필수화는 저장소 관리자가 GitHub 보호 규칙으로 별도 설정한다.

충돌은 양쪽 변경 의도를 확인하고 공통 로직의 의미가 달라지면 관련 담당자와 협의한다. 해결 후 영향받은 테스트를 다시 실행한다. 공유 브랜치의 기록 재작성과 강제 푸시는 팀 합의 없이 수행하지 않는다.

현재 PR 템플릿과 CI 설정은 빈 파일이므로 자동 리뷰나 테스트가 구성된 것으로 간주하지 않는다. CI가 준비되기 전에는 로컬 검증 결과와 한계를 PR에 남긴다.

## 산출물과 증적 관리

| 항목 | 관리 위치 | 기록할 내용 |
| --- | --- | --- |
| 코드와 변경 이력 | GitHub 브랜치, 커밋, PR | 변경 이유, 리뷰 및 검증 결과 |
| 설계와 개발 순서 | `docs/`, `ROADMAP.md` | 구현 계약, 결정 근거, 완료 조건 |
| 기획과 회의 기록 | 프로젝트 Notion | 담당자, 상태, 결정 사항, Issue 및 PR 링크 |
| 공유용 테스트 자료 | `tests/fixtures/`, 승인된 샘플 경로 | 출처, 용도, 민감정보 제거 여부 |
| 원본 증적과 생성 보고서 | 접근 제한 저장소 또는 로컬 산출물 경로 | 대상, 시점, 실행 조건, 결과와 관련 커밋 |

증적에는 대상 Asset 또는 Finding 식별자, 개선 전후 상태, 도구 및 버전, 데이터 기준시점, 실행 조건과 판정 근거를 남긴다. 화면 캡처만으로 성공을 단정하지 않고 SBOM 비교, 재분석 결과와 기능 검증을 함께 확인한다. AI가 작성한 설명은 담당자가 근거와 대조하여 검수한다.

통합 후에는 깨끗한 체크아웃에서 환경 설정, 경로, 의존성과 관련 테스트를 확인한다. 아직 실행할 수 없는 기능은 계획 또는 미구현으로 기록하며 성공 결과를 만들어 적지 않는다.

## 공개 전 확인

- 실제 API 키, 토큰, 비밀번호, 세션 쿠키, 금융정보와 개인정보를 코드, Issue, PR, 로그 및 이미지에 포함하지 않는다.
- 실제 키는 로컬 `.env`에만 두고 `.env.example`에는 빈 값 또는 공개 가능한 기본값만 적는다.
- 현재 `.gitignore`는 `.env`를 제외하지만 `.env.local` 등 모든 변형을 제외하지는 않는다. 새로운 환경 파일을 사용하기 전에 제외 규칙을 확인한다.
- `data/assets/`, `data/sbom/`, `data/threat_intel/`는 자동 제외 대상이 아니다. 공개 가능한 샘플만 명시적으로 추가한다.
- `reports/`의 생성물은 제외되며 `reports/README.md`와 `.gitkeep`은 관리 대상이다. 공유할 증적은 민감정보를 제거하고 접근 범위를 검토한다.
- Lab은 격리된 허가 환경에 두고 플랫폼과 함께 외부에 배포하지 않는다. 상세 공격 절차와 민감한 원본 증적은 공개 자료에 포함하지 않는다.
- 커밋 전 스테이징된 변경을 확인한다. 키가 노출되면 먼저 폐기하고 사용 내역을 확인한다. 파일에서 지운 값도 과거 커밋에는 남으므로 기록 정리는 협업자와 별도로 조율한다.
