# 코드 작성 원칙

Python 기반 SBOM 분석 플랫폼의 일관성, 재현 가능성과 유지보수성을 위한 규칙이다. [AGENTS.md](../AGENTS.md)의 프로젝트 원칙과 디렉터리 책임을 따르며, 협업 절차는 [GitHub 협업 원칙](./github_collaboration.md)을 참조한다.

## 참고 자료와 적용 범위

제공된 `Project Convention`에서 명명, PEP 8, import 순서, 주석 및 환경 설정 원칙을 반영한다. `Team REDRED` 문서에서는 입력 검증, 안전한 DB 접근, 비밀정보 보호, 증적 기반 검증과 사람의 보고서 검수를 반영한다.

참고 자료의 머신러닝 학습 및 추론 구조는 도입하지 않는다. 이 프로젝트의 Risk Priority는 설명 가능한 규칙으로 계산하며 AI는 검증된 데이터를 해석하는 역할만 맡는다. Flask와 Streamlit은 계획된 UI/API 기술이며, 문서에 등장한다고 실행 구현이 완료된 것은 아니다.

## 이름과 코드 형식

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 디렉터리와 Python 파일 | `snake_case` | `core/sbom/`, `kev_client.py` |
| 변수와 함수 | `snake_case` | `asset_context`, `calculate_risk_priority` |
| 클래스 | `PascalCase` | `AssetContext`, `VerificationResult` |
| 상수와 환경 변수 | `UPPER_SNAKE_CASE` | `RISK_WEIGHTS`, `DATABASE_URL` |

PEP 8을 따르고 들여쓰기는 공백 4칸을 사용한다. 기존 UI 페이지명 `Home.py`, `01_Assets.py` 등의 번호 접두 형식과 README에서 정한 경로 예외는 유지한다. 목표 경로와 현재 경로가 다른 경우 명명 규칙 적용만을 이유로 일괄 이동하지 않는다.

함수와 변수 이름은 책임과 의미를 드러내도록 작성한다. `process_data`, `test2`처럼 용도를 알기 어려운 이름은 피한다. 공개 함수와 주요 데이터 구조에는 타입 힌트를 사용하고, 하나의 함수가 하나의 책임을 갖도록 구성한다.

import는 표준 라이브러리, 외부 라이브러리, 프로젝트 모듈 순으로 나누고 그룹 사이에 빈 줄을 둔다. 사용하지 않는 import와 코드는 제거한다. 아직 구현되지 않은 모듈을 문서 예시 때문에 추가하지 않는다.

주석은 판단 이유, 예외 조건과 제약을 설명한다. 외부에서 사용하는 함수나 복잡한 처리에는 입력, 반환값과 주요 예외를 설명하는 docstring을 작성한다. 변수 대입처럼 코드만으로 명확한 내용을 반복하지 않는다.

## 모듈 책임

| 위치 | 책임 |
| --- | --- |
| `app/` | 사용자 입력, API 요청과 응답, core 호출 및 화면 표시 |
| `core/sbom/` | SBOM 생성, 파싱, 정규화와 변경 비교 |
| `core/vulnerability/` | Component 매칭과 CVE, CVSS, CWE, KEV, EOL 정보 처리 |
| `core/assets/` | 금융서비스 및 Asset Context 처리 |
| `core/risk/` | 규칙, 가중치, 점수, Priority와 계산 근거 |
| `core/compliance/` | 관련 보안통제 연결과 근거 관리 |
| `core/consulting/` | 검증된 데이터 기반 설명 및 보고서 초안 |
| `core/verification/` | 개선 증적 확인, 전후 비교와 검증 판정 |
| `database/` | 영속성, DB 엔티티, 저장소 접근과 마이그레이션 |
| `scripts/` | core 기능을 호출하는 독립 실행 진입점 |
| `labs/`, `scenarios/` | 격리된 분석 대상과 별도의 시연 맥락 |

화면과 스크립트에서 Risk 계산이나 외부 취약점 API 호출을 중복 구현하지 않는다. DB 접근은 서비스와 저장소 계층을 통해 수행한다. DB 엔티티를 의미하는 `database/models/`를 머신러닝 모델 저장소로 사용하지 않는다.

## 분석 데이터와 AI

- CVSS와 금융서비스 맥락을 반영한 Risk Priority를 별도 값으로 관리한다.
- Risk Factor와 가중치는 `core/risk/rules.py`에서 관리하고 여러 파일에 상수를 복제하지 않는다.
- 동일한 분석 입력과 규칙 버전은 동일한 결과를 반환하도록 한다. 결과에는 점수, Priority, 적용 조건과 가점 근거를 함께 기록한다.
- 외부 데이터의 출처, 기준시점과 누락 여부를 보존한다. 조회 실패나 알 수 없는 상태를 취약점 없음 또는 안전으로 바꾸지 않는다.
- AI가 CVE, CVSS, CWE, KEV, 구성요소 버전, 자산 관계, EOL, 패치 상태와 검증 결과를 생성하거나 추정하게 하지 않는다.
- AI 설명은 검증된 구조화 입력을 근거로 작성하고 담당자가 검수한다. AI 출력에 따라 Risk Priority 또는 Verification 결과를 변경하지 않는다.
- 보안기준 매핑은 참고용 통제 연결이며 공식 인증 또는 규정 준수 판정으로 표현하지 않는다.

## 입력과 외부 연동

외부 입력은 형식, 타입, 필수 필드, 길이 및 범위를 검증한다. SBOM의 지원 형식과 누락 필드 처리 규칙을 명시하고 지원하지 않는 형식은 이해할 수 있는 오류로 반환한다.

외부 API는 별도 클라이언트로 분리하고 timeout, HTTP 오류, rate limit과 응답 구조를 처리한다. 재시도는 횟수와 대기 시간을 제한하며 재시도 가능한 오류를 구분한다. 캐시를 사용하면 기준시점과 갱신 정책을 남긴다.

SQL에는 파라미터 바인딩 또는 기존 ORM의 안전한 API를 사용한다. 사용자 입력을 SQL 문자열로 조합하지 않는다. API의 자산 및 분석 결과 조회에는 인증과 자원별 접근 권한을 확인한다.

화면 출력은 출력 맥락에 맞게 인코딩하고 신뢰할 수 없는 HTML을 그대로 렌더링하지 않는다. 파일 업로드는 크기와 허용 형식을 검증하고 사용자 파일명을 저장 경로로 직접 사용하지 않는다. 저장 경로를 지정된 영역 안으로 제한하고 업로드 파일을 실행하지 않는다.

## 오류와 로그

예상 가능한 오류는 호출자가 구분할 수 있는 예외나 결과로 전달하고 API 및 UI 계층에서 이해할 수 있는 메시지로 변환한다. 내부 오류 상세와 DB 접속정보를 사용자에게 노출하지 않는다.

무조건적인 예외 무시와 의미 없는 `try/except`를 사용하지 않는다. 부분 실패가 발생하면 성공 범위, 실패 원인과 재시도 가능 여부를 기록한다. 외부 API 장애가 예고 없는 전체 종료로 이어지지 않도록 처리한다.

SBOM 가져오기, 매칭, 위험 계산과 검증 등 주요 단계는 `logging`으로 기록한다. 운영 로그에 `print()`를 사용하지 않으며 디버그 출력을 제거한다. API 키, 인증 헤더, 쿠키, 개인정보와 민감한 원본 응답은 로그에 기록하지 않는다.

## 설정과 의존성

환경별 값은 설정 계층을 통해 읽는다. 실제 키와 접속정보는 로컬 `.env`에 두고 `.env.example`에는 변수명과 공개 가능한 기본값만 기록한다. 비밀값은 오류 메시지, 테스트 fixture와 스크린샷에도 넣지 않는다.

새 패키지를 추가하기 전에 표준 라이브러리와 기존 의존성으로 해결할 수 있는지 확인한다. 추가가 필요하면 PR에 패키지 이름, 사용 이유와 위치를 명시한다. 대형 프레임워크와 머신러닝 의존성을 임의로 도입하지 않는다.

현재 `pyproject.toml`과 `requirements.txt`는 빈 파일이다. 포매터, 린터 및 테스트 도구가 설치되거나 자동 적용된 것으로 가정하지 않는다. 도구를 도입할 때 설정, 실행 명령과 의존성을 함께 문서화한다.

## 테스트와 개선 검증

새 핵심 기능에는 관련 테스트를 함께 작성한다. 특히 Parser, Normalizer, Matcher, Risk Engine, Priority Mapping, SBOM Diff와 Verification을 검증한다.

- 단위 테스트는 정상 입력, 누락 또는 잘못된 입력, 중복 및 경계 조건을 다룬다.
- Risk Rule 변경 시 테스트를 갱신하고 실제 정책의 등급 경계 바로 아래와 경계값을 검사한다. 정책이 확정되지 않은 예시 수치를 구현값으로 사용하지 않는다.
- 외부 API 테스트에는 고정된 fixture나 대역을 사용해 재현성을 확보하고 실패, timeout, 빈 응답을 포함한다.
- 통합 테스트는 SBOM부터 Risk까지, 개선부터 Verification까지 모듈 간 계약과 데이터 전달을 확인한다.
- Verification은 점수 하락만으로 성공 처리하지 않는다. SBOM 변화, CVE 재분석, 재스캔 및 기능 정상동작 등 계획된 증적을 확인한다.
- 증적 부족은 성공으로 처리하지 않는다. 실패와 Risk Accepted를 구분하고 예외 승인 근거를 기록한다.

Finding 상태는 `Open`, `Recommendation Created`, `Remediation Applied`, `Verification In Progress`, `Verification Passed`, `Verification Failed`, `Risk Accepted`를 공통 Enum 또는 상수로 관리한다.

현재 테스트 구현은 비어 있으므로 테스트 파일 존재만으로 검증 완료라고 적지 않는다. 실제 실행 명령, 결과와 미검증 범위를 PR에 기록한다.

## 완료 기준

변경된 기능은 실행 가능하고 기존 동작을 유지해야 한다. 필요한 테스트와 오류 처리를 확인하고, 결과의 근거 및 재현성을 설명할 수 있어야 한다. 분석 및 DB 계약이 바뀌면 관련 설계 문서도 함께 수정한다.

구현 완료, 테스트 통과, 개선 성공은 각각의 증거가 있을 때 기록한다. 미구현 기능, 남은 문제와 다음 작업을 명확히 남긴다.
